\chapter{考察}\label{cha:Discussion}
本研究では、テストケースと要求仕様書の対応関係の確認にかかる時間の削減を目的として、
テストケースを可視化するTCVダイアグラム(Test-Case Visualization Diagram)
の自動生成ツール\tool{}(VIsualization of Testcase Tool)を試作した。
本章では、まず、評価実験を行い、\tool{}の有用性に関する評価を行う。
次に、\tool{}と関連研究を比較する。
最後に、\tool{}の問題点について述べる。

% \tool{}の有用性に関する評価
\section{\tool{}の有用性に関する評価}
\tool{}の有用性を評価するため、\tool{}を使用する場合と使用しない場合で、
テストケースの過不足箇所(\ref{sec:words}節参照)の発見にかかる時間に対する実験を行う。

実験の事前準備として、要求仕様書とテストスイートの組を2つ用意した。
1つ目は、「閏年判定システム」に関する要求仕様書とテストスイートの組である。
具体的には、図\ref{fig:reqspec}に示した要求仕様書と、図\ref{fig:testsuite_1}および図\ref{fig:testsuite_2}に示したテストスイートの組である。
以降、この要求仕様書とテストスイートの組を、組$\alpha$と呼ぶ。
2つ目は、「成績付けシステム」に関する要求仕様書とテストスイートの組である。
用意した要求仕様書を図\ref{fig:exp_reqspec_b}に、テストスイートを図\ref{fig:exp_testsuite_b1}、図\ref{fig:exp_testsuite_b2}、および、図\ref{fig:exp_testsuite_b3}に、それぞれ示す。
以降、この要求仕様書とテストスイートの組を、組$\beta$と呼ぶ。
組$\beta$に対して、\tool{}が出力したTCVダイアグラムを、図\ref{fig:tcv_seiseki2}に示す。

なお、組$\alpha$および組$\beta$には、それぞれテストケースの抜け箇所を1件、不備箇所を1件、および、過剰箇所を2件、合計4件を意図的に含めた。

実験に参加する被験者は、宮崎大学で情報工学を専攻する4人(以降、被験者A〜Dと呼ぶ)の学生である。
被験者A、Bの2人は組$\alpha$に対して\tool{}を使用し、組$\beta$に対して\tool{}を使用せずに、実験を行う。
被験者C、Dの2人は組$\alpha$に対して\tool{}を使用せずに、組$\beta$に対して\tool{}を使用し、実験を行う。

\tool{}を使用する場合では、
\tool{}が出力したTCVダイアグラム(\ref{sec:testcase_visualization_diagram}節参照)を確認し、
被験者が全てのテストケースの過不足箇所を見つけるまでにかかった時間を、発見時間として計測する。
\tool{}を使用しない場合では、
CSVファイルに記述した要求仕様書とテストスイートを確認し、
被験者が全てのテストケースの過不足箇所を見つけるまでにかかった時間を、発見時間として計測する。

以下に、実験の手順を示す。
\begin{enumerate}
    \item 実験者は、発見時間の計測を開始する。
    \item 被験者は、作業を開始し、全てのテストケースの過不足箇所を発見したと判断した時点で、実験者へ報告を行う。
    \item 実験者は、計測を一時停止し、被験者の発見結果を確認する。
    発見漏れが無い場合、計測を終了する。
    発見漏れがある場合、実験者は、発見漏れの箇所を記録し、
    発見漏れがあることを被験者に伝え、計測を再開した上で手順$2.$に戻る。
\end{enumerate}

表\ref{tb:exp_result}に示すように、組$\alpha$に対して\tool{}を使用した場合、

テストケースの過不足箇所の発見にかかる時間を、平均で3分 54秒(約80.7\%)削減できた。

以上のことから、TCVダイアグラムを自動生成する\tool{}は、
テストケースの過不足箇所の発見にかかる時間の削減に有用であるといえる。

\subsection{テストケースの過不足箇所の発見漏れに関する考察}
本節では、テストケースの過不足箇所の発見漏れに関して、考察を行う。

評価実験において、\tool{}を使用しなかった場合、
被験者Aは、図\ref{fig:exp_testsuite_b2}に示した組$\beta$のテストケースの過剰箇所であるTC-8「単位付き数値入力テスト」を、
被験者Dは、図\ref{fig:testsuite_1}に示した組$\alpha$のテストケースの過剰箇所であるTC-5「閏年の2月日数表示テスト」を、
それぞれテストケースの過不足箇所として発見できなかった。
発見漏れが生じた原因は、CSVファイルに記述した各要求仕様のテキストと各テストケースのテキストの内容を1つずつ確認し、
テストケースの過不足箇所を見つける作業が煩雑であったためであると考察する。

一方、\tool{}を使用した場合、
テストケースの過不足箇所の発見漏れは生じなかった。
発見漏れが生じなかった原因は、\tool{}が出力するTCVダイアグラムが、
テストケースの過不足箇所に該当する要求仕様およびテストケースの各矩形要素を、
品質種別に応じた背景色(表\ref{tab:quality_type}参照)で強調表示するので、                                                                                                             
視覚的にこれらの箇所を容易に識別できたためであると考察する。

以上のことから、TCVダイアグラムを自動生成する\tool{}は、
テストケースの過不足箇所の発見に有用であると考察する。

\section{関連研究}\label{sec:related_work}
西らは、テスト観点をモデリングするための記法である
NGT(Notation for Generic Testing)を中心とした
テスト開発プロセスVSTeP(Viewpoint-based Software Test Engineering Process)
を提案した\cite{vstep1}\cite{vstep2}。
また、VSTePの中で、テスト設計支援手法として、
Reverse VSTePを提案した\cite{re-vstep}。
Reverse VSTePとは、既存の(十分設計されていない)テストケース群から
テスト観点モデルをリバースモデリングして改善する手法群である。
この手法では、テストケースからテスト観点モデルを作成することにより、
テストケースのテスト観点を可視化することを目的としている。
これに対して、\tool{} が出力するTCVダイアグラムは、
テストケースと要求仕様の対応関係を分析し、
テスト観点ではなく、
テストケース自体を可視化することを目的としている点が異なる。

松井らは、自然言語で記述した要求記述とテストケース記述の類似度に基づいて、
要求に対するテストの網羅性を可視化する、要求カバレッジ可視化手法を提案した\cite{matsui2018}。
この手法では、各要求記述と各テストケース記述をそれぞれ1つの文書としてベクトル化し、
文書間のコサイン類似度を算出する。
そして、各テストケース記述を最も類似度が高い要求記述に関連付けることによって、要求カバレッジを可視化する。
要求カバレッジは、ミクロな観点とマクロな観点の2種類で可視化する。
ミクロな観点では、各要求記述に関連付いたテストケース記述の数、内容、および類似度をHTML形式で出力する。
マクロな観点では、要求記述間の類似度と各要求記述に関連付いたテストケース記述の数をばねモデルのグラフ形式で出力する。
松井らの手法では、要求記述とテストケース記述の文書全体の類似度を算出し、
各要求記述に関連付いたテストケース記述の数で網羅性を判断する。
そのため、テストケース記述が要求記述に関連付いた場合でも、
テストケース記述の内容が要求記述を十分に検証できているかは判断できない。
これに対して、\tool{}は、要求仕様とテストケースの対応付け要素
(「前提条件」と「事前条件」、「トリガー」と「操作」、「システム応答」と「期待出力」)
ごとに類似度を算出し、各対応付け要素の類似度が閾値以上であるかを個別に判定する。
これにより、\tool{} が出力するTCVダイアグラムは、
要求仕様に対して対応関係はあるが、一部の対応付け要素の類似度が閾値未満であるテストケースの不備箇所や、
対応する要求仕様が存在しないテストケースの過剰箇所を強調表示できる。
すなわち、要求仕様の内容とテストケースの内容との比較に基づいた可視化を行っている点が異なる。

\section{\tool{}の問題点}\label{sec:problem}

\tool{}の問題点を、以下に示す。

\begin{itemize}
    \item 要求仕様とテストケースの対応関係が一対一のみを対象としている問題\\
    現状の\tool{}では、入力対象のテストスイート(\ref{subsec:testsuite}節参照)の条件において、
    「各テストケースは1つの要求仕様のみを検証対象とし、
    同一の要求仕様を検証するテストケースは複数存在しない」としている。
    そのため、1つの要求仕様に対して複数のテストケースが存在する場合や、
    1つのテストケースが複数の要求仕様を同時に検証する場合を対象としていない。
    この問題は、Word2Vec\cite{word2vec}やBERT\cite{bert}などの単語分散表現を用いて、単語や文をベクトル化し、
    要求仕様とテストケース間の意味的な類似度を用いて、
    一対一以外の対応関係を抽出するようアルゴリズムを改良することで解決できると考える。

    \item 対応付けのパラメータの設定における問題\\
    \tool{}の機能を使用する際、ユーザーは、初期設定(\ref{sec:config}節参照)で記述する設定ファイルvitt.yamlにおいて、
    要求仕様とテストケースの対応関係の有無を判定する際に用いるパラメータを、適切に指定する必要がある。
    しかし、これらのパラメータの最適な値は、対象とするシステムによって異なるため、
    ユーザーが試行錯誤しながら調整する必要があり、手間と時間がかかる。
    この問題は、複数の閾値で試行した結果を比較する機能や、過去の対応付け結果を学習し、
    パラメータを自動調整する機能を追加することで解決できると考える。

    \item TCVダイアグラムのスケーラビリティの問題\\
    \tool{}が出力するTCVダイアグラムは、全ての要求仕様の矩形要素とテストケースの矩形要素を、1つの図として表示する。
    そのため、要求仕様やテストケースの規模が拡大すると、矩形要素の数が多くなるため、
    図が複雑になり、全体像の把握が困難になる。
    この問題は、特定の要求仕様やテストケース、
    または、要求仕様とテストケース間の対応関係の状態を表す
    品質種別に対してフィルタリングして表示する機能を実装することで解決できると考える。
\end{itemize}
